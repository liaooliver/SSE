01概觀：一位使用者、一位協調者，指揮三家模型

「安裝進度即時串流」（FastAPI + SSE）這個應用，不是由單一對話框一路寫到尾，而是由一套多 AI Agent 協作流程完成： 最上層只有一位人類（使用者）與一位協調者（使用者直接對話的 Claude Code session），底層再依職責分派給來自三家不同模型廠商的獨立 worker（materials/CLAUDE.md、materials/ORCHESTRATION.md）。

決策與管理
使用者 ↔ 協調者
使用者負責規格核准與關鍵決策（D1–D12、E1–E11）；協調者只管派工、稽核、守關卡，不動手寫交付物。
廠商一：Claude Code
實作／規格／瀏覽器
透過 claude -p 與 claude -p --chrome 執行實作、編輯規格合約、實機瀏覽器 E2E。
廠商二：Codex CLI
獨立測試／審閱
透過 codex exec 在未放入 app/ 的工作區，純粹照 SPEC 與合約寫測試並參與審閱。
廠商三：agy（Gemini）
合約／驗證／驗收
透過 agy -p 負責合約比對、突變抽檢、非視覺 HTTP E2E、clean clone 驗收與迴歸檢查。

為什麼要刻意湊齊三家不同的模型家族？

核心理由只有一個：獨立交叉驗證（independent cross-checking）。 同一個模型家族往往有相似的解讀習慣與盲點——如果讓同家族模型既寫程式又寫測試，兩邊可能對同一個邊界條件做出相同假設，導致測試全過卻偏離規格。 因此這套設計讓 Claude 寫實作、Codex（GPT-6.2）盲寫測試、agy（Gemini 4）當裁判與驗證者；在 materials/ORCHESTRATION.md:87 甚至明文規定：為了保持三家模型不同，agy 也禁用 Claude 模型。

協調者的鐵律與歷史例外（materials/CLAUDE.md:5-7、materials/PROGRESS.md:3-21,159-163） 規則定案後，協調者是純管理者：不親自編輯 app/、tests/、docs/SPEC.md 或 pyproject.toml，不自己跑 pytest／uvicorn／curl 驗證，絕不閱讀測試原始碼，也不替使用者核准關卡。每次新開 session，必須依 PROGRESS.md 的接手檢查清單確認背景 worker（pgrep）、最後一筆日誌與 git log 狀態後再接續。
專案紀錄中的三項歷史例外：① T0.1、T1.1、T1.4 是協調者在「只做管理」規則確立之前親自執行（偏差 X1）；② T0.7（撰寫 AGENTS.md、加嚴 ruff／mypy 與搬運骨架）是在使用者明確指示下由協調者完成（偏差 X3）；③ T1.8（以 SVG 為主軸重寫 docs/SPEC.md v1.0 與 contracts/）是由使用者直接指定的 agy session 完成，未經規格編輯 worker 的 brief／report 流程（決策 D10、偏差 X5，見 materials/plans/spec_v1_plan.md:3-7,15-21）。

02整體架構圖

整套系統運作在單一 macOS 本機環境中，核心設計是「一份共用的規格與合約（Single Source of Truth）＋ 五個分開的工作區目錄（搭配工具權限與事後稽核）＋ 結構化的 briefs/、reports/、evidence/ 交換目錄」（materials/ORCHESTRATION.md:18-55、materials/PROGRESS.md:165-172）。

03角色與權限分工

這套團隊劃分了 6 種明確角色（1 位協調者＋5 類 worker）。每個角色的寫入範圍與讀取禁區都白紙黑字定義在 materials/ORCHESTRATION.md:7-14 與 materials/PROGRESS.md:8-19；正式派工時，tests-ws 除了規格與合約外，也會同步 AGENTS.md、pyproject.toml 與鎖定依賴（materials/PROGRESS.md:80,171,195）：

為什麼實作與測試必須由不同廠商、互不見面地寫？

  • 防止測試退化成實作的鏡像：tests-ws 未放入 app/，且規則禁止 Codex 讀取 app/ 與主 repo，使其只能依賴 docs/SPEC.md（行為）、contracts/openapi.yaml（HTTP 形狀）與 contracts/domain.pyi（Python 公開符號），以黑箱角度檢驗規格（materials/ORCHESTRATION.md:30-40）。
  • 防止實作對測試過度擬合：impl-ws 未放入 tests/ 且規則禁止讀取測試；即使 Phase 3 測試失敗，協調者也只轉交 agy 寫出的「需求 ID＋預期行為＋實際行為」描述（例如 T3.5 修正 R10 第 9 項時，紀錄掃描與快照比對皆未發現存取外部路徑，見 materials/PROGRESS.md:96）。
  • 讓合約缺口自然浮現：在 Phase 2 雙盲並行開發時，雙方各自撞上規格沒說死的地方，立刻回報 CONTRACT GAP 與 CONTRACT CONFLICT——例如後端與測試同時指出 script_for 拿不到 run_id 但 R8 要求 run_started 帶 run_id，以及 R9 去空白規則與 OpenAPI pattern 衝突（materials/reports/p2-impl-backend.md:80-93、materials/reports/p2-codex-tests.md:81-89）。這套分工的設計目的，正是降低同一模型對模糊處做出一致假設而未被察覺的風險。
  • 避免協調者無意洩題：協調者依規則也不讀測試原始碼，只看 Codex 的「測試名稱 → R-id」對照表與 agy 的行為摘要，設計目的是避免在派工 brief 中無意透漏測試寫法（materials/ORCHESTRATION.md:54）。

04隔離與事後稽核機制

使用者在 Phase 0.5 決定採用「分開目錄＋工具權限＋事後稽核」，不使用容器（決策 D3，materials/ORCHESTRATION.md:42-55）。這是一個在開發速度與安全邊界之間的務實取捨：啟動負擔低，但必須坦承讀取無法從技術上阻擋，改由每次跑完的事後稽核彌補。

實務上，事後稽核也確實需要人工判斷誤報。例如 T2.1a 跑完後，搜尋紀錄時曾命中 .orchestra，協調者進一步核對上下文，確認那只是實作者讀取工作區內的 .gitignore 內容，而非越界存取主 repo，這才放行並記明於 materials/PROGRESS.md:196。另外，在 T2.6 與 T3.5 中，協調者將實作者權限從 --dangerously-skip-permissions 收窄為 acceptEdits 搭配 Bash(uv:*)，雖在 T3.5 發現唯讀的 sed／cat／ls 未被擋下（皆在 impl-ws 內、無害），該次快照比對與紀錄掃描未發現越界存取或修改（materials/PROGRESS.md:88,96）。

05一個任務的生命週期

從派工到提交，worker 任務遵循一套可重複、可中斷接手的標準流水線（materials/ORCHESTRATION.md:103-153）。因為 macOS 沒有內建 GNU timeout，規則檔（決策 D6）以 perl -e 'alarm 1800; exec @ARGV' -- 作為預設 30 分鐘逾時的政策範例；實務上各任務 brief 另依工作量載明不同時限（例如 T6.4b 寫 20 分鐘、T4.4 寫 40 分鐘、T4.1–T4.3／T6.3／T6.4 寫 45 分鐘），而管理紀錄未逐次記載外層實際傳入的 alarm 秒數（materials/briefs/p4-claude-browser.md:18、p4-agy-e2e.md:20、p6-claude-browser.md:27、p6-claude-browser-recheck.md:21）。

實際呼叫 Worker 的指令（規則範例見 materials/ORCHESTRATION.md:109-119）

以下 T 代表政策範例中的逾時包裝器 perl -e 'alarm 1800; exec @ARGV' --，W 為 ~/.local/share/sse-orchestra。下方保留影響執行與稽核的完整旗標，並另外標註 T2.5 實戰中 agy 的實際啟動差異： 

# Claude 實作者（規則範例；stream-json 供事後稽核）
cd $W/impl-ws && T claude -p "$(cat brief)" --model claude-opus-5-5 --effort high \
  --dangerously-skip-permissions \
  --append-system-prompt "You are a worker. Follow the brief only." \
  --output-format stream-json --verbose > log

# Claude 規格編輯（規則範例；禁止 Bash 與網路）
cd $W/spec-ws && T claude -p "$(cat brief)" --model claude-opus-5-5 --effort high \
  --permission-mode acceptEdits --allowedTools "Read,Edit,Write,Glob,Grep" \
  --disallowedTools "Bash,WebFetch,WebSearch" --output-format stream-json --verbose > log

# Claude 瀏覽器 E2E（規則範例；限 127.0.0.1:<port> 新分頁）
T claude -p "$(cat brief)" --chrome --model claude-sonnet-5-5 --effort high \
  --dangerously-skip-permissions --output-format stream-json --verbose > log

# Codex 審閱（唯讀沙盒）
T codex exec -m gpt-6.2-sol -c model_reasoning_effort=high \
  -s read-only -C $W/tests-ws --skip-git-repo-check -o report - < brief

# Codex 寫測試（工作區可寫沙盒）
T codex exec -m gpt-6.2-astra -c model_reasoning_effort=high \
  -s workspace-write -C $W/tests-ws --skip-git-repo-check -o report - < brief

# agy 審閱（規則範例；唯讀計畫模式）
T agy -p "$(cat brief)" --mode plan --model gemini-4-neon-high > report

# agy 驗證／E2E／驗收（規則範例 ORCHESTRATION.md:119）
cd $W/verify-ws && T agy -p "$(cat brief)" --dangerously-skip-permissions --model gemini-4-neon-high > report
# ↑ T2.5 實戰記錄（PROGRESS.md:87,204）：該帳號不支援 --mode auto，實際以預設模式＋--sandbox 執行：
cd $W/verify-ws && T agy -p "$(cat brief)" --sandbox --model gemini-4-neon-high > report

06Phase 0–6 流程與關卡

整個專案從空 repo 到最終 Preline 介面改版交付，共經歷 Phase 0 至 Phase 6（含中途補立的 0.5 環境搭建、0.6 Python 環境與 2.5 合約檢查）。每個關鍵轉折都設有硬關卡，確保未達標絕不往下流（materials/ORCHESTRATION.md:57-68、materials/PROGRESS.md:44-57）。

實際同步啟動與執行重疊整理
  • Phase 1（明文記載同步啟動）：T1.2（Codex 審閱）‖ T1.3（agy 審閱）同時在背景啟動（materials/PROGRESS.md:179）。
  • Phase 2（明文同步啟動＋可確認重疊）：T2.1a（Claude 後端實作）‖ T2.2（Codex 撰寫測試）於 23:35 同時在背景啟動；T2.1a 於 23:46 完成後接續派出 T2.1b（23:49 完成），整個 T2.1b 落在 T2.2（23:52 完成）回報之前，兩者有明確執行重疊（materials/PROGRESS.md:195-198）。
  • Phase 3（明文記載同步啟動）：T3.5（Claude 修 R10#9）‖ T3.6（Codex 補涵蓋缺口與強化時序）同時在背景啟動（materials/PROGRESS.md:210）。
  • Phase 6（兩組明文同步啟動＋一組執行區間交錯）：日誌明文記載並行啟動的有兩組——T6.3（agy 迴歸）‖ T6.4（瀏覽器 E2E）與修正後的 T6.3 重跑 ‖ T6.4b 補驗（materials/PROGRESS.md:226,228）；至於 T6.1（Preline 改版）與 T6.2（更新 AGENTS.md），日誌僅記載同於 20:50 備妥任務說明，並於 20:51 與 21:10 先後完成，未明記是否同時啟動（materials/PROGRESS.md:224-226）。
  • 刻意錯開不並行：Phase 4 原本架構允許 agy 與瀏覽器並行，但實際排程刻意先跑完 T4.1–T4.3 再啟動 T4.4，避免瀏覽器負載干擾 AC11 效能量測（materials/PROGRESS.md:213）。

07失敗怎麼分派與真實案例

當 Phase 3、4 或 6 出現失敗，協調者不自己猜誰錯，而是依據獨立驗證方（agy 或瀏覽器 E2E）的分類結果進行路由；規格模糊則可由 agy 或協調者判定後提報使用者。同一個問題最多來回 3 輪，若第 3 輪重驗仍未通過就升級交給使用者裁決，避免 AI 之間陷入無窮互踢皮球（materials/ORCHESTRATION.md:69-77）。

專案中的三個真實分派案例

案例一（Phase 3）：2 個 IMPL BUG＋測試缺口，雙線並行 1 輪收斂

T3 首次執行 pytest 回報 71/73（T3: FAIL），agy 判定 2 個失敗皆為 IMPL BUG（違反 R10 第 9 項：apply_event 未驗證 run_started 欄位型別與 log.ts），另在測試審查中列出 R14／R15／R19／R25／R26 涵蓋缺口與 7 個時序敏感節點（materials/reports/p3-agy-verify.md:36-55,97-118）。協調者同步派工：只給行為描述讓 Claude 實作者修 app/domain.py（T3.5），同時把缺口與時序風險比照 TEST BUG 交給 Codex（T3.6）。其中 R25（無執行中 task 的中斷復原）因無法透過公開介面固定中斷點，T3.6 記錄為不可做確定性測試而未增補；其餘缺口補齊後，第 2 輪重驗（T3r2）達成 75/75 ×3 全過且 7 項目標突變全殺（materials/PROGRESS.md:92,96-98）。

案例二（Phase 4）：瀏覽器實測發現 SPEC 歧義 → 使用者裁決 E4 → 規格編輯

T4.4b 實測「串流途中停掉伺服器、再用同一個資料庫重啟」（檢查 A3）時，頁面靠 EventSource 自動重連就補齊並結束，並未重跑整套同步流程（materials/reports/p4-claude-browser-b.md:31-45）。這與 R27 字面的「網路錯誤 → 3 秒後重跑同步流程」出現解釋空間。協調者判定為 SPEC AMBIGUOUS 提報使用者，使用者裁決 E4（算符合、補寫一句），再由 Claude 規格編輯（T4.5）升級 docs/SPEC.md 至 v1.1.3 並同步各工作區（materials/PROGRESS.md:102-103,147,216-218）。

案例三（Phase 6）：視覺瑕疵 → T6.1-fix1（第 1 輪）→ 雙重並行重驗 PASS

Preline 視覺改版後，T6.4 瀏覽器 E2E 回報 T6.4: FAIL（0 deviations, 1 visual issue）：展開無錯誤框的 task 卡片時，log 框上方留白 16 px、下方卻有 28 px（materials/reports/p6-claude-browser.md:63-67）。協調者打開截圖 R3-02 確認後，派 T6.1-fix1（第 1 輪）。實作者查出根因是 Tailwind v4 的 space-y-3 對隱藏的 .error-box 仍生效，只改 2 個 class 字串（taskBody 去掉 space-y-3、errorBox 改加 mt-3）。隨後並行重跑 T6.3 重跑 與 T6.4b 瀏覽器補驗：無錯誤框時淺色／深色上下留白皆量得 17 / 17 px（含 1 px 邊框，實質內距 16 / 16 px），顯示錯誤框時量得 17 / 12 / 17 px（log 至錯誤框 12 px 為刻意的 mt-3），兩邊同時 PASS（materials/PROGRESS.md:112,227-229、materials/reports/p6-claude-browser-recheck.md:5-16）。

11實戰經驗與教訓

這套流程並不是一開始就完美無瑕；許多最重要的防護措施，都是跑出問題後從日誌與回報裡長出來的。以下整理 9 條有實際紀錄支撐的教訓：

  1. 1. 日誌時間戳絕對不要用「估計值」，要以真實時鐘與 commit 為準 協調者在 2026-11-20 23:49 之後一度憑感覺填寫日誌時間，結果日誌時間跑在真實系統時間前面，事後不得不回頭對照 git commit 時間修正（materials/PROGRESS.md:203），且在 materials/git-log.txt:13,15 還留下兩筆專門修時間的 commit（PROGRESS: fix log time）。
  2. 2. 原始執行紀錄在稽核通過後立刻刪——但先確保沒有第二個協調者同時在跑 stream-json 與原始 log 非常龐大，稽核通過並抽出精簡回報後立刻刪除能保持目錄乾淨（materials/ORCHESTRATION.md:150）。但偏差紀錄 X4 踩過一個痛坑：22:33 時另一個協調者 session 同時在跑，提前 commit 刪掉了 T0.6 的原始 log（c36be5f），導致 T0.6 無法做越界稽核（materials/PROGRESS.md:161）。同時只能有一位協調者。
  3. 3. Worker 的 CLI 旗標必須以實際帳號環境驗證，不能只照文件寫 ORCHESTRATION.md:119 原本寫 agy 使用 --dangerously-skip-permissions，但實戰 T2.5 時被 auto mode 擋下；改試 --sandbox --mode auto 又發現該帳號不支援 --mode auto，最後實際落地的是「預設模式＋--sandbox」（materials/PROGRESS.md:87,204）。
  4. 4. 並行跑 E2E 要切開連接埠區段，效能量測則應避開重負載並行 Phase 6 同時跑 T6.3（agy）與 T6.4（瀏覽器）時，協調者明確將兩者的 127.0.0.1 埠號切為 18000–18399 與 18500–18599，避免撞埠或誤殺對方 uvicorn（materials/PROGRESS.md:226）。Phase 4 則刻意等 agy 跑完 AC11 效能測試再啟動瀏覽器 E2E，避免搶 CPU 失真（materials/PROGRESS.md:213）。
  5. 5. 協調者寫的 Brief 也會出錯，獨立驗證方能幫忙揪出來 T6.3 brief 的 D.2 要求用 git diff --exit-code app/static/index.html 證明重建產物與交付版一致，但在當次執行中 verify-ws 的 git 索引（與 HEAD）仍對應改版前的基準 commit，改版檔案屬未暫存變更，執行該指令必然回傳 exit 1。首輪 T6.3 中 agy 指出此問題，改以建置前備份搭配 cmp 與 shasum 驗證（materials/reports/p6-agy-regression.md:99-101）；修正後的 T6.3 重跑 則改以建置前備份搭配 git diff --no-index --exit-code 與 shasum -a 256 驗證（materials/reports/p6-agy-regression-r2.md:114-116）。另外 T2.7 brief 指定的 pragma 註解用了全形括號 （B1），協調者事後察覺會觸發 Ruff RUF003，透過 --resume 同一 session 改成半形 (B1)（materials/PROGRESS.md:89）。
  6. 6. 沙盒無網路限制要靠「事前預同步＋事後清暫存」配合 Codex 的 -s workspace-write 沙盒不能連網且預設 uv 快取不可寫。協調者因此在派工前先對 tests-ws 執行 uv sync --frozen，讓 Codex 用 UV_NO_SYNC=1 與暫存快取目錄跑 uv run --offline 離線檢查，跑完再清掉系統暫存區殘留的 t36-uv.*（materials/PROGRESS.md:97,195,203、materials/reports/p2-codex-tests.md:93）。
