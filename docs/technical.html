專案在做什麼

選「磁碟空間不足」再按安裝，畫面會走完準備和下載。直到「複製檔案」顯示第 24 行紅字，使用者才看到模擬的寫入失敗。此時左側能定位失敗階段，右側保留該工作的輸出和排除建議。這就是專案要解決的問題：只知道整輪安裝失敗，還不足以判斷該處理哪一步。

一輪安裝依序經過準備環境、下載套件、安裝、設定，每階段各有三個工作。頁面先用 GET /install/plan 取得完整計畫，再依執行進度標出每個節點。情境選單取自 GET /install/scenarios（R12），每項只有 id、label、fail_task_id；下表的失敗行數及代碼來自後端劇本。

系統架構

先沿著啟動路徑讀圖，再看回到瀏覽器的兩條資料來源。安裝請求交給背景模擬器後，頁面可以離線。寫入事件是安裝程序的工作，訂閱者只決定自己讀到哪一筆。

create_app 建立獨立的 FastAPI 實例，掛上三個路由。進入 lifespan 才開啟資料庫、執行復原，並將 Runtime 掛在 app.state.runtime。設定在建立 app 時解析，優先採明確傳入的參數（值非 None），其次為環境變數，最後採預設值。

資料庫路徑 SSE_DB_PATH 預設為 ./install.db。相鄰日誌的間隔 SSE_LOG_INTERVAL 預設為 0.15 秒，閒置心跳間隔 SSE_HEARTBEAT_SECONDS 為 15.0 秒，每個訂閱者的佇列容量 SSE_SUBSCRIBER_QUEUE_SIZE 為 1000 筆。

HTTP 入口也提供兩種不同的觀測。GET /health 傳回 {"status":"ok"}；GET /stats 的 subscribers 表示正在重播或接收即時事件的連線數，可以在開關分頁時觀察。R16 規定回 404、204 或 reset 的連線不計入。實作先登記再讀取資料庫，確認屬於這些分支才退訂；若同時查詢統計，計數可能短暫包含尚在判斷的連線。

從命令追到執行中的工作

app/main.py 把開關資源的責任放在生命週期。這讓測試能用同一個工廠指定資料庫路徑、日誌間隔、心跳及佇列容量，再觀察各 app 各自的行為。

app/routers/install.py 經 RuntimeDep 取得執行環境。回快照時把領域物件轉成 HTTP 模型；串流請求則先判斷游標，決定要回歷史與即時事件、要求重新同步，或直接結束。

app/schemas.py 在路由邊界檢查情境名稱。輸入可忽略多餘欄位，快照輸出則明確定義階段、工作和錯誤物件，客戶端可依合約讀取。

app/runtime.py 保留背景工作的參考。它在相鄰兩筆日誌之間等待 log_interval（預設 0.15 秒），其他事件直接寫入、廣播。關機時取消模擬器並結束串流。

從一筆事件追到畫面

app/domain.py 的 script_for 決定事件的順序與內容。劇本本身可重現；實際輪次、序號與 UTC 時間等到寫入才確定。

app/store.py 以一個受鎖保護的 SQLite 連線執行交易。快照讀出同一輪的事件後，依序套用 apply_event。安裝路由和執行環境透過 asyncio.to_thread 呼叫同步的儲存方法。

app/broker.py 逐一用 put_nowait 投遞。遇到滿佇列就移除該訂閱者並通知連線停止，其他佇列仍可繼續收件。

app/sse.py 負責每個 ASGI 回應。傳送資料、等待用戶端斷線、等待訂閱停止三者並行；其中一項結束後清理其餘工作，最後關閉產生器、退訂。

frontend/src/index.html 把狀態對應到可反覆使用的 DOM 節點。frontend/src/input.css 提供這些節點使用的樣式，frontend/build.mjs 將編譯結果放入模板。下一節的快照模型正是這個頁面同步時的起點。

資料模型與狀態機

一輪安裝（run）由情境與 run_id 識別。階段（stage）包含有順序的工作（task），工作識別碼在整份計畫中唯一。每一行日誌（log）屬於一組 stage_id、task_id。工作內部的 line_no 從 1 起算，跨工作的事件順序則看整輪共用的 seq。

initial_snapshot 建立尚未套用事件的領域物件，輪次為 running、last_seq = 0，所有階段與工作為 pending。實際 HTTP 快照至少包含第一筆 run_started。apply_event 每次產生新快照，會檢查輪次一致、序號恰為上一筆加一、欄位型別正確、目標存在且狀態容許。日誌只能寫給執行中的階段及工作，結束後再套用事件會引發 ValueError。

資料庫的 runs 表存 id、scenario、status；events 表的主鍵是 (run_id, seq)，另存事件 type、JSON 格式的 data 和帶時區的 UTC 時間 ts。工作錯誤和日誌本文都隨事件持久化。快照中的階段與工作狀態由事件重建，訂閱者佇列、頁面選取及展開狀態只活在記憶體。

SSE 的 id 把兩個整數組成 <run_id>.<seq>。例如 3.57 表示第 3 輪第 57 筆事件。去除首尾空白後，兩側都必須是 ASCII 十進位數字。輪次遞增、每輪序號重新從 1 開始，因此舊分頁手上的游標同時說明它屬於哪一輪。

SSE 在這個專案的應用

啟動是一次請求，進度是一連串回應資料

使用者只要送一次 POST /install。接下來，資料的方向一直是伺服器往頁面推送。若定期輪詢，頁面得決定多久查一次，閒置時也會送查詢；若採 WebSocket，這條進度通道又用不到雙向傳訊。此處選 SSE，一個普通 HTTP GET 即可逐筆送出具名文字事件，瀏覽器的 EventSource 同時處理重連和上次收到的 ID。

GET /install/events 成功開流回 200。Content-Type 以 text/event-stream 開頭，Cache-Control: no-cache, no-transform 限制快取與中間層轉換，X-Accel-Buffering: no 要求代理停用緩衝；回應不壓縮。送出第一個區塊表示訂閱與歷史讀取已就緒，該區塊單獨寫 retry: 3000，告知瀏覽器重連間隔為 3,000 毫秒。

線上格式與九種資料事件

以下是用本專案的儲存層建立第一輪成功情境後，交由 format_event 編碼的第一筆資料。data 只有一行 JSON；末尾空白行標示區塊完成，讓瀏覽器可以分派 run_started。

id: 1.1
event: run_started
data: {"run_id":1,"scenario":"success"}
事件名稱單筆 data 內容讀者可以得知什麼
run_startedrun_id（整數）、scenario（字串）劇本起點加上實際輪次。
stage_started、stage_succeeded、stage_failedstage_id對應階段開始、成功或失敗。
task_started、task_succeededstage_id、task_id工作屬於哪一階段，以及何時展開或收合。
logstage_id、task_id、line_no、level、text、ts行號是整數；層級為 info 或 error；時間為帶時區的 UTC 字串。
task_failedstage_id、task_id、error_code、message、hint定位失敗工作，顯示錯誤代碼、原因與排除建議。
run_finishedresult值為 succeeded 或 failed。送完即正常結束串流。

閒置時，伺服器在 heartbeat_interval（預設 15 秒）沒有輸出後送一個 : ping 註解和空白行。每次輸出後重新計時，持續閒置就重複送；資料與心跳同時就緒時優先送資料。心跳不會變成頁面上的一行安裝日誌。retry、心跳及要求重新同步的 reset 都是控制訊息，沒有資料事件序號，也不寫入 SQLite。

快照切在哪裡，串流就從哪裡接手

假設使用者在下載中重新整理。先以 GET /install 取得輪次、每個節點的狀態，以及同一個讀取交易所涵蓋的最後序號 S。這份快照足以把下載標成執行中，但工作下方的文字仍要補回。

頁面固定 until=S，從 after=0 讀 GET /install/logs，每次都帶 run_id。伺服器只回 after < seq ≤ until 內的日誌，依序排列；有下一頁就用 next_after 當新下界，直到它為 null。預設每頁 500 筆，可指定 1 至 1,000。補讀途中產生的事件會落在 S 之後，留給串流。

接著頁面開啟 /install/events?last_event_id=<run_id>.<S>。伺服器先為這個訂閱者建立專屬的有界佇列並登記訂閱，再從資料庫讀大於 S 的已提交事件。重播後，佇列中若也有剛送過的資料，便丟棄 seq ≤ last_sent 的項目。這個先後次序同時處理「訂閱前已經發生」與「讀歷史時才發生」的事件。

例如第 57 筆同時出現在重播與佇列，重播播到 57 後會略過佇列的 57。若瀏覽器此時斷線，已收到的 ID 為 3.57，重連就從第 3 輪大於 57 的事件接續。

游標的優先順序與邊界

第一次連線用查詢參數 last_event_id；同一個 EventSource 收過帶 id 的事件後，瀏覽器重連時會用 Last-Event-ID 標頭送回最後收到的事件 ID。合法標頭優先於合法查詢值；無效標頭視為缺席。路由先驗證查詢參數，若有帶但格式錯誤，直接回 422。

目前輪次 R、最後序號 L端點的回答
尚無任何一輪404。
無起點從這一輪的 seq = 1 重播。
起點屬於其他輪次；或同輪執行中，起點大於 L先送 retry，再送無 id 的 reset，其 data 只有當前 run_id，然後關閉。
同輪已結束，起點大於或等於 L204 No Content，瀏覽器停止重連。
同輪的其他合法起點 n送出 seq > n。若執行中且已追平，等待即時事件；遇到 run_finished 結束。

頁面用 addEventListener 監聽九個具名事件，從 lastEventId 解析輪次與序號，解析 JSON，再依類型更新工作、階段或輪次。它會忽略舊連線的回呼和已套用的序號；輪次錯誤、無法解讀 ID 或 JSON 則重新同步。run_finished 關流，reset 關流後重讀快照。

正常流程

把圖 3 換成實際的成功輪次來看。選 success 送出後，伺服器先寫入第 1 筆，再回 202。不論使用者何時同步，最後一張快照都會反映同一批事件。下表的序號可由固定劇本逐筆計算，用來對照串流很方便。

整輪序號這段完成的工作頁面如何呈現
1run_started，建立輪次顯示執行中，停用安裝按鈕。
2–35準備環境，依序檢查作業系統、磁碟與相依套件工作開始即展開，每行附加到工作下方，成功後收合。
36–89下載套件，先取清單，再下載並驗證雜湊自動跟隨開啟時，右側切換到下載階段。

失敗流程

回到磁碟不足的例子。copy_files 原定輸出 40 行，這個情境先產生 23 行正常日誌。第 24 行改成 level: "error"，文字為「磁碟空間不足，/opt 剩餘 0 MB」。下一筆 task_failed 才帶齊錯誤詳情；若只看紅字日誌，就會漏掉排除建議。

實際欄位名是 error_code，此處為 E_DISK_FULL。message 與錯誤日誌相同，hint 是「請釋放至少 2 GB 空間後重新安裝」。兩者與代碼一起保存在工作快照的 error。下一個工作 register 和後續設定階段維持 pending；重新整理仍可用快照與補讀重現原因。

若當時開著自動跟隨，失敗後已沒有執行中的階段，頁面依 C2 選中失敗階段。若使用者正在手動查看別的階段，選取會保留；可以按「恢復自動跟隨」回到錯誤現場。

重試與恢復流程

連線掉了，安裝繼續：瀏覽器自動重連

執行中收到 error 且 readyState 是 CONNECTING，頁面的 #run-status 顯示「連線中斷，瀏覽器重新連線中…」。它保留現有快照、日誌和同一個 EventSource。瀏覽器重連同一個網址。若已收到帶 id 的事件，就以 Last-Event-ID 標頭續接。若連第一筆帶 id 的事件都還沒收到，重連請求沒有這個標頭，伺服器沿用網址中的 last_event_id=<run_id>.<S>，從快照序號之後開始送。

舊連線斷開時，伺服器清理訂閱。若是慢速訂閱者塞滿佇列，伺服器也只結束該連線；其餘訂閱者與模擬器照常執行。被中斷的頁面再次連上時仍由 SQLite 重播。

程序停了，重啟時替舊輪次收尾

收到關機訊號時，執行環境停止模擬、結束串流。若程序停在某筆已提交的事件之後，資料庫可能留有 running 的輪次。用同一個資料庫重啟，Runtime.start 在對外服務前呼叫 Store.recover，從已落盤的序列還原最後狀態。

若中斷時有執行中的工作，補上的 task_failed 含 E_INTERRUPTED、「伺服器在安裝途中停止」、「請重新安裝」。這條復原路徑直接補失敗事件，不另外製造一行錯誤日誌。若只有輪次開始，便可直接用 run_finished 將它結束。已完成的前綴保留，後續序號連續；使用者可在同一輪快照中看見結果。

依據　docs/SPEC.md R24–R25 · app/main.py · app/runtime.py · app/store.py

使用者按下安裝，建立新的一輪

失敗後可以重新選情境並按安裝。POST /install 收到合法情境後，以同一寫入交易檢查有沒有進行中的輪次。這個檢查也涵蓋兩個分頁同時按安裝的情況。

成功時刪除前一輪及其事件，建立較大的 run_id，同時寫入新的 run_started。模擬器已排入背景執行。頁面收到 202 後呼叫 sync()，以快照的 last_seq 為界補讀日誌，再從該界線之後接收事件。此時快照可能已超過第 1 筆。固定計畫從頭執行，頁面保留手動選取階段的偏好。情境不合法或 JSON 有誤為 422，已在執行為 409，頁面都在狀態列顯示錯誤。發起安裝的請求失敗時，頁面不會定時重送該命令。

C1 的限制出現在跨分頁操作。一輪結束後，本頁已停止監聽。若其他分頁此時開始新一輪，本頁仍顯示舊結果；再按安裝可能得到 409，需重新整理才能看到進行中的輪次。

依據　docs/SPEC.md R14、R27（C1、C3） · app/store.py · app/routers/install.py · app/schemas.py · frontend/src/index.html

頁面自己重試：依失敗的位置回到正確入口

同樣是「3 秒」，呼叫的函式可能完全不同。首次載入要先取得計畫與情境；快照同步則建立在畫面結構已經備妥的前提上。實作採固定 3 秒間隔，沒有指數退避。

若 GET /install/logs 回 404，它屬於同步失敗，要排程重試；只有讀快照的 404 代表此處的正常空畫面。已結束的一輪也會先載入快照並補完日誌，再開流；若起點已追平，端點回 204，頁面不排程同步。

每次進入 sync 都會增加 generation、關掉上一條串流、清除舊計時器。尚未完成的讀取返回時，只有世代仍吻合的結果能更新畫面，避免較慢的舊請求覆蓋新輪次。

依據　docs/SPEC.md R13、R15、R18、R27（C4、E4–E6） · frontend/src/index.html · app/routers/install.py

前端

同一份進度，保留使用者正在查看的位置

R26 固定六個元素 ID。#scenario 和 #install-btn 用來選情境及啟動安裝，#run-status 顯示輪次狀態或錯誤。#stage-list 列出階段，#task-list 顯示所選階段的工作，#follow-btn 可恢復自動跟隨。

頁面啟動時以 Promise.all 同時取得計畫與情境；建立左側階段與右側工作節點，再同步目前輪次。run 保存輪次資訊，stageStatus 和 taskState 保存狀態，lastApplied 記錄已套用的最大序號。每個工作另有已顯示日誌的序號集合，重複日誌不會再追加。

跟隨模式先選執行中的階段；若沒有，依序選失敗階段、計畫中最後一個非 pending 的階段、第一個階段（C2）。使用者點目前的階段仍會跟隨；點別的階段時才切成手動選取。只有 #follow-btn 能恢復跟隨，重新按安裝也會保留手動模式（C3）。

工作開始時展開並捲到日誌底部，成功時收合。點標題可查看先前日誌，資料與節點都留在分頁中，展開毋須發送 HTTP 請求。工作失敗時頁面將它展開，紅色錯誤框顯示代碼、原因與建議。R27 要求失敗工作保持展開；實作自動展開後，使用者仍能點標題手動收合。標題的 aria-expanded 與內容可見性同步，階段與工作則以 data-status 反映狀態。文字以 textContent 寫入。

測試與驗證

先驗證劇本，再測 HTTP 與串流，最後才讓真正的 TCP 斷線。這樣可以分清「狀態算錯」和「事件在傳輸中漏掉」。測試依公開介面觀察，重播結果可以直接與輪次結束後的快照比對。

類別與檔案用什麼方式驗證需求／驗收
單元 · tests/test_domain.py比對固定計畫、七種劇本、合法與非法轉移、事件 ID、資料與控制區塊格式。R4–R10、R19–R20、R22（AC5）
HTTP · tests/test_http.py測 app 隔離與設定、空資料庫、請求驗證、分頁界線，以及並發啟動時只有一輪成立。R2–R3、R9、R11–R18、R25（AC8）

經驗分享與設計取捨

先決定讀取邊界，再分頁

如果每翻一頁就改用當下的最後序號，補讀的範圍會隨安裝進度移動。把快照的 S 固定為每一頁的上界，日誌才能與畫面上的狀態對齊；之後的每一筆都交給同一條串流。這個界線比「目前第幾頁」更有用。

依據　app/store.py · frontend/src/index.html · docs/SPEC.md R13、R15、R27

輪次和位置要一起存

只有序號 57，無法辨認它屬於舊安裝還是新安裝。AUTOINCREMENT 保證重裝後的輪次更大，複合事件 ID 則讓端點能區分「同輪續傳」和「必須讀新快照」，即使舊事件已經清除也能正確回答。

依據　app/store.py · app/domain.py · app/routers/install.py

先落盤，才有重播的依據

SQLite 開啟 WAL，寫入按序提交後才通知訂閱者。看到事件的頁面掉線時，那筆事件已可從同一份歷史讀回。單一連線與鎖讓交易順序容易追查，同時也意味同一個儲存物件的讀寫會排隊；同步 I/O 移到工作執行緒，讓事件迴圈繼續服務連線。

讓重播與即時傳送短暫重疊

假如讀完歷史才登記訂閱，中間新提交的一筆可能既沒被查到，也沒進佇列。先登記會有少量重疊，但 last_sent 足以判斷哪筆送過；前端再保留 lastApplied，兩個邊界各有明確的檢查位置。

慢分頁的成本由該連線承擔

應用程式送出一行，中間層也要讓它通過

即使程式每次產生一個事件，代理若把回應累積成批次，使用者仍無法逐行看進度。停用代理緩衝、要求不轉換內容、每個區塊各送一個 ASGI 訊息，是同一條傳送路徑上的三個設計決定；驗證時要一起查看標頭與實際讀到的區塊。
